# 自适应专家层

[English](../../configuration/adaptive.md)

GPU 只容纳模型专家的一部分。自适应层追踪会话的路由去向，把使用最多的专家移入 VRAM，轮次在 decode 之旁进行。以下设置塑造这些轮次。内置取值是这里实测最快的；本页说明每项的取舍以及测过的结果。

## 一轮如何工作

引擎统计每个专家被路由到的次数。一轮把不在 VRAM 的专家按次数排序，收益明确时，将路由最多的换入，替换驻留中最少被路由的。在服务器上，一轮分三步，各占一个 decode 窗口：离开的专家被复制到 RAM，进入的专家在旁流上被复制进它们的槽位，下一个窗口即使用它们（每层只等待自己那一层的复制）。上一轮落地之后才会开始新一轮，所以"每个窗口"约等于每三个窗口一轮。每轮之后所有计数都乘以 decay，近期路由因此重于早期。

主卡的一轮把所有层放在一起排序，所以路由到更多专家的层会从路由到更少专家的层手中拿走槽位；对等卡持有的专家要有更大的计数才能移到主卡，而主卡为它让出的专家无论属于哪层都交出其对等槽位，因此没有任何专家同时坐在两块卡上。有对等卡时，主卡先拿它的那份，对等卡再按层逐一拿下主卡未持有、路由次数次多的专家。exclusive peer placement 和层分割按层逐一排序。在两块卡上（400 W + 180 W，冷 prose，四个 seed），把全部层放在一起排序在相同窗口宽度下把窗口成本降低了 1.9%，在请求的前 50 个窗口降低 6-15%。一种保留对等副本的晋升让两块 GPU 各损失一个专家：一段很长的 JSON 回复之后，对等卡五分之一的槽位被这种副本占据；在单台服务器的标准 bench 顺序（conv、struct、prose；四个 seed）下，prose 为 269 tok/s、struct 为 562，而交出槽位时分别是 284 和 573。一轮排序出的换入数少于 `adapt-swaps` 时，至多拿其中的 16 个给 CPU 层专家（它们近期大约只被路由过一次：计数从 1 到排序下限），每个都对照一个驻留专家、其计数至少高出一次路由：prose 会碰到许多各只碰几次的专家，而它们在主要排序下会留在 CPU 上。在两块卡上（400 W + 180 W，冷 prose，两个 seed），它在头 150 个窗口之后于相同窗口宽度下把窗口成本降低约 3%；没有这 16 个的上限时，一段 JSON 回复慢了 1.2%。

移动一个专家会改变由哪个层计算它的行（CPU 与 GPU 的舍入不同），所以开启自适应后的输出并非每次运行按位相同；见[精度](../precision/index.md)。

## 设置

| 设置 | 默认值 | 作用 | 取舍 |
| --- | --- | --- | --- |
| `adapt-every` | 服务器上 `1`，有无对等层都一样；层分割以及不在 `--serve` 下时 `4` | 每 N 个 decode 窗口一轮。`0` 保持专家按加载时的位置。 | 更少、更晚的轮次对链路开销更小，但请求会按旧放置运行直到下一轮：全新引擎要等 N 个窗口才有第一轮，话题切换也要等同样久。 |
| `adapt-swaps` | `96`（`0` = 关闭） | 一轮换入主卡的最大专家数。上一轮候选数达到该值两倍以上的服务器轮会换入四倍数量（冷启动或话题切换）。 | 更大的轮次追赶更快，但每轮搬运更多字节（每个 NVFP4 专家约 2.6 MiB，离开的专家没有 RAM 副本时是双程），并且这些复制与 CPU 专家争夺宿主内存。RAM 副本保留四倍 N 个空位（默认下 384 个空位，约 1 GiB），从存放专家的 RAM 中划出。 |
| `peer-adapt-swaps` | `adapt-swaps` 的值 | 一轮换入对等卡的最大专家数。 | 同上，作用在对等的链路上；`0` 冻结对等层，对代码类请求影响最大。 |
| `adapt-decay` | 服务器上 `0.85`，有无对等层都一样；层分割以及不在 `--serve` 下时 `0.7` | 每轮后所有计数所乘的系数。 | 越低遗忘越早、跟话题切换越快；越高越保持长期放置，但适应变晚。decay 是按轮的，所以 `adapt-every` 更大时，同一个值按窗口算记住的时间长得多。 |
| `expert-profile-save` | 关闭 | 在退出时以及每隔 `expert-profile-save-every` 分钟（默认 10）在请求之间保存学到的放置（VRAM 中的专家，连同计数）。启动时找到该文件就按它放置，而不是模型自带的 profile。需要开启自适应层。 | 延续的工作负载在它学到的放置上启动；换一个工作负载则在错误的专家上启动，必须先换出来。 |

`done` 行的 `hit=` 是主卡查询中由其 VRAM 服务的比例。对等卡计算的专家和经 PCIe 读取的专家不在这些查询之列，所以 `hit` 更高未必请求更快：请比较 `tg` 速率。

## 这里测得的结果

一块 RTX 5090（400 W），单独或搭配一块 180 W 的 RTX 5060 Ti 作为对等层，NVFP4 pack，8 个 CPU pool worker，
每一组都使用相同的服务器设置。每一组是一个全新服务器加一个由 31 个贪心请求组成的会话：一个 1200 token 的冷 prose 请求（要紧的数字）、8 个 prose 请求、12 个 code 请求、4 个 prose 请求和 6 个各 400 token 的短聊天请求。速率是引擎的 decode 速率（tok/s）；"switch" 是 prose 之后的头三个 code 请求。每组跑一次：冷 prose 请求的重复在两块卡上约波动 1.2%、单卡 0.3%（下面更小的缓存下为 4%）。

两块卡上单独调一个旋钮：`adapt-every 64` 代价最大（冷启动 195.1、switch 120.2、整场 183.7）；`adapt-swaps 256` 单独（冷启动 290.7、整场 290.7）和 `adapt-decay 0.7` 单独（冷启动 287.3、整场 296.0）都在默认值的噪声范围内。拖长的周期才是真正的伤害：全新引擎的第一轮要等 N 个窗口，之后每次话题切换都要按旧放置运行同样久。更大更少的轮次补偿不了这一代价；默认设置下约每三个窗口一轮，在 decode 期间把主卡链路保持在约 7-8 GB/s 的专家复制上，仍是最快的一组。保存的 profile 对长周期那组的首个请求有帮助（它在学到的专家上启动），但对其余会话没有帮助；并且在单卡上它还拖慢了默认组的首个 prose 请求，因为那个 profile 学到的是会话最后的工作负载（聊天），不是 prose。

用更小的缓存（仅 RTX 5090，`expert-cache 4300`，其常规槽位的一半，相当于更小的卡），`adapt-swaps` 取 48、96 和 160 时冷启动分别为 130.3、127.1 和 132.4（默认值跑了两次），132.3 tok/s：在那里换入数量同样只影响运行噪声。

## probe 会选出这些

[basalt-probe](../probe.md) 在其运行的机器上，用单一引擎尝试内置取值、`64 / 256 / 0.7` 和 `1 / 160`：`PROBE adapt` 在每次尝试前把各层恢复到加载后的原位，所以每次运行都是冷启动后接一次话题切换（先 prose 1200 token，再 struct 400）。只有当某设置超出其噪声带胜过内置取值时它才打印该设置；带 `--expert-profile-save FILE` 时它还会说明从 FILE 启动是否有帮助。在这里（400 W + 180 W，以及单卡 400 W），复位运行的成绩与全新引擎头两个请求处于同一噪声水平（两块卡：内置 283.9 和 285.8 对全新 283.6、`1 / 160` 的 285.2 对 290.5；单卡：224.3 和 225.8 对 225.9、`1 / 160` 的 231.2 对 230.6 tok/s），probe 在两组卡上都没有打印任何 adaptive 设置（`1 / 160` 相对 3% 噪声带为 +0% 和 +3%，`64 / 256 / 0.7` 为 -29% 和 -42%），保存的 profile 也没有。

## 其他机器

未测量：两块相同的卡（专家层或层分割）、主卡不超过 16 GB（槽位少得多，miss 更多、积压更大）、更慢或更窄的链路（每轮落地更久），以及空闲空位会把专家挤出 RAM 副本的那个 RAM 容量档位。以上测量对这些场景的暗示，作为未经验证的指引：

- 在服务器上把 `adapt-every` 保持在小值。长周期会饿死冷启动和每次话题切换，而保存的 profile 只能修正与所学工作负载相符的启动。
- 更慢的链路下，每轮更少换入优于更少轮次：先调低 `adapt-swaps`，再考虑抬高 `adapt-every`。
- RAM 紧张时，`adapt-swaps` 决定空位数量（四倍 N 个专家）：调低它就把这些 RAM 还给专家。
- 用你自己的标志跑 `basalt-probe`；想匹配自己的负载组合，就用全新服务器尝试某个改动并比较各 `done` 行的 `tg` 速率，把第一个请求排在最前。
